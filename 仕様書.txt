# システム仕様書：Web小説構造・描写監査スクリプト (Automated Novel Auditor)

## 1. システム概要
本システムは、カクヨムなどのWeb小説テキスト（エピソード単位のファイル群）を順次読み込み、LLM（Claude API または ローカルOllama）を用いて「組織力学・政治劇の合理性」および「作劇上の都合によるキャラクターの作為的無能化・知性低下」を自動判定・監査するCLIプログラムである。

各エピソード単位で逐次監査と文脈メモリ（`currentMemory`）の更新を行い、最終的に全セッションの指摘ログを統合・要約して「構造監査報告書」を生成・出力する。

## 2. 動作環境・依存関係
* **実行環境**: Node.js（ES Modules 形式 / Native `fetch` および `AbortController` をサポートする環境）
* **標準モジュール**: `fs`, `path`
* **連携外部 API / サービス**:
  * **Ollama (ローカルLLM)**: `http://localhost:11434/api/chat`
  * **Anthropic Claude API**: `https://api.anthropic.com/v1/messages`

## 3. 設定パラメータ（定数一覧）
| 定数名 | 型 | デフォルト値 / 設定値 | 説明 |
| :--- | :--- | :--- | :--- |
| `USE_CLAUDE` | Boolean | `false` | `true`: Claude API を使用 / `false`: Ollama を使用 |
| `OLLAMA_API_URL` | String | `'http://localhost:11434/api/chat'` | Ollama のチャットエンドポイント URL |
| `OLLAMA_MODEL_NAME` | String | `'qwen-64k'` | Ollama で使用するモデル名 |
| `CLAUDE_API_URL` | String | `'https://api.anthropic.com/v1/messages'` | Claude API のエンドポイント URL |
| `CLAUDE_MODEL_NAME` | String | `'claude-3-5-sonnet-20241022'` | 使用する Claude モデル名 |
| `ANTHROPIC_API_KEY` | String | `process.env.ANTHROPIC_API_KEY` | Claude APIキー（環境変数より取得） |
| `INPUT_DIR_NAME` | String | `'kakuyomu_episodes'` | 入力テキストファイルが格納されているディレクトリ名 |
| `MAX_CHARS_PER_REQUEST` | Number | `15000` | LLMリクエスト時の1回あたり上限文字数（切り詰めの閾値） |
| `LOG_SUMMARY_THRESHOLD`| Number | `12000` | 累積ログの中間要約を発動させる文字数閾値 |
| `MAX_TOTAL_CHARS` | Number | `500000` | 全体で読み込む累計テキストの上限文字数 |
| `CHUNK_SIZE` | Number | `1` | 1回の監査セッションで処理するエピソード数 |
| `NUM_CTX` | Number | `16384` | Ollama 呼び出し時のコンテキストウィンドウサイズ |

## 4. 機能仕様および処理フロー

### 4.1 コマンドライン引数
* `--partial`: **部分読みモード**を有効化。後続の伏線や未登場設定の存在を考慮し、未解決の描写に対して一定の宥恕（ゆーじょ）を持たせる監査プロンプトに切り替える。

### 4.2 主要処理フロー (`main` 関数)
[1. コマンドライン引数の解析]
    │  process.argv から '--partial' の有無を判定。
    ▼
[2. 入力ファイルの取得・パース]
    │  INPUT_DIR_NAME 内の .txt ファイルを取得し、自然順ソート（1, 2, 10...）。
    │  各ファイルから「作品名」「エピソード名」「本文」をパース。
    ▼
[3. エピソード単位の順次監査ループ (auditChunk)]
    │  CHUNK_SIZE (1話) 毎に本文を取得。
    │  累計読み込み文字数が MAX_TOTAL_CHARS を超えた時点でループ終了。
    │  `auditChunk` を実行：
    │    ├─ 前回の文脈メモリ (currentMemory) と最新本文をLLMに入力
    │    ├─ 最新の世界観・組織メモを抽出して currentMemory を更新
    │    └─ 指摘事項（作為的無能描写）の有無を判定し、ログ蓄積
    ▼
[4. ログの肥大化チェック & 中間圧縮 (summarizeAllLogs)]
    │  全セッション終了後、累積指摘ログが LOG_SUMMARY_THRESHOLD (12,000字) を
    │  超えている場合、ログを分割要約・圧縮して結合する。
    ▼
[5. 最終構造監査報告書の生成 (generateFinalSummary)]
    │  整理された監査ログを基に、最終的な批評要約レポートをLLMに生成させる。
    ▼
[6. 結果出力]
    │  コンソールに各話判定ログ、最終メモ、および構造監査報告書を出力。

## 5. モジュール・関数仕様

### 5.1 `callLLM({ systemContent, userContent, temperature = 0.3 })`
LLMに対する共通通信APIインターフェース。`USE_CLAUDE` の値に応じて呼び出し先を動的に切り替える。
* **タイムアウト制御**: 10分（600,000ms）で `AbortController` によるリクエスト中断を行う。
* **Claude API 呼び出し時**: `x-api-key` および `anthropic-version: 2023-06-01` ヘッダーを付与し、`max_tokens: 4000` で POST。
* **Ollama 呼び出し時**: `options: { num_ctx: NUM_CTX, temperature }` パラメータを付与して POST。

### 5.2 `truncateText(text, maxChars, label, keepEnd = false)`
テキストが指定文字数 (`maxChars`) を超えた場合に切り詰めるユーティリティ関数。
* `keepEnd = true`: 前半を省略し、末尾（最新の文脈情報）を残す。
* `keepEnd = false`: 後半を省略し、冒頭部分を残す。

### 5.3 `extractMemory(responseText, previousMemory)`
LLMのレスポンス出力から正規表現を用いて `■ 最新の世界観・組織の力学メモ` セクションを抽出する。
* **フォールバック処理**: 抽出に失敗した場合（形式不一致等）、警告ログを出力しつつ前回の記憶 (`previousMemory`) を維持する。

### 5.4 `extractIncompetence(responseText)`
LLMのレスポンス出力から正規表現を用いて `■ 作為的無能・描写の歪みの指摘` セクションを抽出する。

### 5.5 `isIssueDetected(incompetenceText)`
抽出された指摘テキスト内に明確な問題提起が存在するかどうかを判定する。
* テキスト内に「なし」「見受けられません」等の非検出キーワードのみが含まれている場合は `false` を返し、具体的な不自然さの指摘が存在する場合は `true` を返す。

### 5.6 `summarizeAllLogs(fullLog)`
累積された指摘ログ (`fullLog`) が `LOG_SUMMARY_THRESHOLD` を超えた際に呼び出される。
* ログを `LOG_SUMMARY_THRESHOLD` 単位で分割（`chunkText`）し、LLMに各ブロックを1,000字程度へ要約させる。要約された各ブロックを再結合して返す。

### 5.7 `auditChunk(title, episodes, currentMemory, isPartialRead)`
各エピソード（チャンク）を監査するコア関数。
* **監査プロンプトの設計方針**:
  * **マクロ視点**: 国家・組織・勢力として当然取るべき初期対応（公式声明、調査の派遣、危機管理ラインの稼働等）の不自然な放置（＝組織レベルの作為的無能）を厳しく見抜く。
  * **ミクロ視点**: プロット進行や主人公等の特定キャラを引き立てるために、登場人物が不自然な失言・粗雑な判断・過度な警戒感の欠落（＝個人レベルの作為的無能）を起こしていないかを検証する。
* **応答フォーマット規定**:
  1. `■ 最新の世界観・組織の力学メモ`: （次話へ引き継ぐ設定・文脈の更新）
  2. `■ 作為的無能・描写の歪みの指摘`: （客観的な不自然さの指摘、または「なし」）

### 5.8 `generateFinalSummary(title, finalResult, isPartialRead)`
全エピソードの検証で蓄積された実際の指摘データ (`finalResult`) を集約し、カクヨム応援コメントやレビュー文面として活用可能な300〜400文字程度の「構造監査報告書」を生成する。
* 単なるあらすじのまとめを厳禁とし、組織論理の破綻や展開都合によるキャラクターの知性低下に対する批評を中心に出力させる。

## 6. 入力ファイルフォーマット仕様
入力ディレクトリ (`kakuyomu_episodes`) 内の各 `.txt` ファイルは、以下のフォーマットを想定している。

作品名：作品タイトル
エピソード：第1話 エピソードタイトル
────────────────────────────────────
（ここにエピソード本文）

* **作品名**: `作品名：` 行から抽出（最初に処理されたファイルから作品全体のタイトルとして保持）。
* **エピソード名**: `エピソード：` 行から抽出。
* **本文**: `──────`（ハイフン/罫線記号が複数並ぶ区切り線）以降を本文としてパース。
* **フォールバック処理**: 区切り線が存在しない場合は、ファイル名（拡張子除く）をエピソードタイトルとし、ファイル全文を本文として扱う。

## 7. 例外処理・エラーハンドリング
* **API タイムアウト制限**:
  LLMからの応答が 10 分を超えた場合、`AbortError` をキャッチして処理のフリーズを防ぎ、エラーメッセージを表示して安全に中断・終了処理を行う。
* **HTTP ステータスエラー**:
  Claude API または Ollama から `200 OK` 以外のレスポンスが返された場合、レスポンスボディとステータスコードを出力して処理を停止する。
* **フォーマットパース失敗時の安全策**:
  LLMの出力が指定のセクション見出しを含まない場合、正規表現のパース失敗を検知し、前回の記憶 (`currentMemory`) を維持したまま次のエピソードの解析を継続する。
* **対象ファイル不在 / 全文字数上限到達**:
  解析対象の `.txt` ファイルが存在しない場合、あるいは累計処理文字数が `MAX_TOTAL_CHARS` を超えた場合、例外を出さずに現在のログのみを出力して安全に終了する。
